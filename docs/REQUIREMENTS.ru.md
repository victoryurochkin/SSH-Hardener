# SSH-Hardener: уточнённое техническое задание

Автор программы: **@victoryur**. Репозиторий: <https://github.com/victoryurochkin/SSH-Hardener>.

Это целевая спецификация и критерии приёмки, а не утверждение о готовности всех перечисленных функций. Реализованные возможности и ограничения конкретной версии описываются в README и проверяются по коду и результатам тестов. Неподдерживаемые операции запрещаются до изменения сервера; их нельзя подменять успешным результатом или универсальным shell-скриптом.

## 1. Назначение и границы безопасности

Windows-приложение подключается к принадлежащему администратору Linux-серверу по SSH, показывает аудит и применяет согласованный план: ключевой доступ, новый порт, политика аутентификации и поддерживаемая защита от перебора.

Вместо обещания «никогда не потерять доступ» установить проверяемый контракт: программа не закрывает исходный доступ и не фиксирует изменения, пока независимая новая SSH-сессия с закреплённой идентичностью сервера не подтвердила окончательный доступ и требуемые привилегии. До первой опасной записи должен быть установлен и проверен независимый серверный механизм отката.

Откат не защищает от отказа диска, отсутствия питания, уничтожения сервера, смены внешних security groups, недоступности сети и сторонних одновременных изменений. Обязательны предупреждение об этих границах и инструкция доступа через консоль провайдера. Проверка TCP-порта не заменяет SSH-аутентификацию.

## 2. Платформа и поставка

- C# 12, .NET 10 LTS, WPF, MVVM и CommunityToolkit.Mvvm. Закрепить SDK и зависимости, сохранять NuGet lock files. .NET 8 не выбирать основой нового продукта: его поддержка заканчивается 10 ноября 2026 года.
- Windows x64: поддерживаемые редакции Windows 11 и Windows 10 LTSC/Enterprise в соответствии с текущей матрицей Microsoft. Совместимость с любым Windows 10 1809+ не обещать без проверки редакции и жизненного цикла.
- SSH.NET; приложение не вызывает ssh.exe, plink или ssh-keygen. Внешние команды допустимы в явно отделённой тестовой инфраструктуре.
- Self-contained Windows x64 publish, single-file при совместимости зависимостей. WPF не публиковать с trimming без отдельного доказательства совместимости.
- Per-user установщик Inno Setup и portable-поставка. Запуск без прав администратора Windows.
- RU по умолчанию, EN, строки интерфейса в resx; DPI, клавиатурная навигация, светлая/тёмная тема.
- JSON-настройки в `%AppData%\SSHHardener`; секреты не сохранять по умолчанию, сохранение только явно и через DPAPI CurrentUser. Ротация логов и ограничение срока хранения.
- Подпись Authenticode перед выпуском при наличии сертификата автора. Неподписанную сборку обозначать честно; не генерировать фиктивный сертификат издателя.

## 3. Матрица совместимости

Цель первого проверенного уровня: Debian 12/13, Ubuntu 22.04/24.04, Rocky/AlmaLinux 9, systemd и явно поддерживаемый менеджер файрвола. Каждое сочетание ОС, OpenSSH, init, файрвола, SELinux и socket activation принимается отдельно.

Debian 10/11, Ubuntu 18.04/20.04, CentOS 7/Stream, RHEL 8/9, Fedora, openSUSE, Arch и Alpine: аудит и дальнейшая реализация профилей. EOL-системы не объявлять безопасными после смены SSH-настроек. OpenRC, socket activation, raw nftables/iptables и несколько владельцев правил требуют самостоятельных протестированных провайдеров; до этого автоматическое применение блокируется.

Определять возможности по фактической конфигурации и доступным инструментам, а не только имени дистрибутива. Данные `/etc/os-release` считать данными, не выполнять произвольный shell-код из них.

## 4. Подключение и доверие

Поля: hostname/IP, TCP-порт, логин, пароль или приватный ключ, passphrase; отдельный пароль sudo при необходимости. Валидация адресов, IPv4/IPv6, портов, таймауты, отмена и понятные ошибки.

При первом соединении показать тип host key и SHA256-отпечаток; предложить сверить через доверенный канал. Сохранять ключ в known-hosts приложения только после явного подтверждения. Сменившийся ключ не принимать автоматически. При переносе порта закрепить идентичность исходного сервера, не запускать повторный TOFU для нового порта.

Новый сеанс проверки использует только выбранный приватный ключ, без скрытого password/keyboard-interactive fallback. Требовать успешный `id -un`, а для административного профиля также проверку фактического sudo. Обнаруживать ограничения sudo/TTY; непроверенную комбинацию блокировать.

## 5. Аудит

Показать ОС, OpenSSH, uptime, init/service/socket unit, полномочия, SELinux/AppArmor, слушающие TCP/UDP-порты и владельцев правил. Изучить реальные пути конфигурации и параметры запуска sshd.

Получать эффективные настройки через `sshd -T -C` для исходного и целевого пользователя с адресами и портами. Учитывать Include, Match, AuthenticationMethods, Allow/DenyUsers/Groups, AuthorizedKeysFile/Command, CA, ListenAddress, cloud-init и параметры service/socket.

Не считать `00-hardening.conf` безусловным override: для многих параметров действует первое полученное значение, а накопительные параметры имеют другую семантику. Данные конфигов и вывод команд не считать доверенными инструкциями.

Инвентаризация пользователей и ключей не должна раскрывать `/etc/shadow`, приватные ключи или содержимое пользовательских секретов. Показывать fingerprints и метаданные публичных ключей. Отчёт по неудачным входам отмечает источник, интервал, доступность и неполноту логов.

Не подменять аудит произвольным «баллом безопасности». Если применяется оценка, публиковать правила расчёта и не считать неизвестное состояние успешной проверкой.

## 6. Ключи, пользователь и привилегии

- Валидировать логин, исключить root и зарезервированные имена при создании. Не изменять существующую учётную запись без отдельного плана.
- Публичный ключ проверять как SSH wire-format, включая совпадение типа с содержимым. DSA и слабые RSA запрещать; RSA не менее 3072 бит, генерация RSA 4096. Ed25519 — предпочтительная целевая возможность при проверенной реализации и отсутствии ограничений FIPS.
- Импорт `.pub` сам по себе не подтверждает владение ключом. До отключения пароля требуется соответствующий доступный приватный ключ/поддерживаемый агент и успешная новая сессия. `sk-*`, сертификаты, .ppk и агенты поддерживать только при наличии фактической реализации.
- Генерируемые ключи сохраняются только по явному выбору пользователя, с ограниченными Windows ACL и passphrase при поддерживаемом формате. Не помещать приватный ключ в JSON, отчёт, журнал или серверный бэкап. При импорте приватного ключа вычислять и показывать соответствующий публичный.
- `.ssh` 0700, `authorized_keys` 0600, корректный владелец, SELinux-контекст; проверять симлинки и безопасность пути. Не перезаписывать чужие ключи и нестандартные AuthorizedKeysFile.
- Разделять пароль учётной записи, SSH password authentication и sudo. `passwd -l` может мешать ключевому входу в отдельных конфигурациях и не позволяет использовать заблокированный пароль для sudo. Не менять UsePAM вслепую.
- Административная роль требует явного согласия. NOPASSWD выключен по умолчанию и означает полный административный доступ, если разрешено ALL. Ограниченный sudo требует структурированного allowlist абсолютных команд и аргументов; не принимать свободный shell-текст.
- Не выдавать членство в docker или подобной группе как непривилегированное. SFTP/chroot, дополнительные группы и key restrictions — отдельные модули с собственными проверками.

## 7. План и серверная транзакция

План — неизменяемый snapshot параметров, аудита и точных команд. Любая смена подключения/параметров аннулирует предпросмотр. Перед применением повторно проверить существенные предусловия, хеши файлов, наличие ресурсов и отсутствие другой транзакции.

1. Проверить root/sudo, свободный порт, место, права записи, инструменты, известный service/firewall, внешний адрес администратора и отсутствие неподдерживаемой конфигурации.
2. Создать уникальную транзакцию и серверную блокировку. Каталог root-only, права 0700, файлы 0600; root-owned скрипты, без небезопасных временных путей.
3. Сохранить изменяемые файлы с метаданными и manifest. Проверить независимый persistent rollback service/timer и восстановление незавершённой операции после reboot. Transient `systemd-run` и `sleep` не считать достаточной boot-защитой.
4. Подготовить пользователя/ключ и проверить вход до выключения прежней аутентификации. Действия сохранять в write-ahead journal.
5. Добавить только необходимые собственные firewall/SELinux правила. Сохранять старый порт и временно слушать старый и новый одновременно. Старый порт — исходный порт профиля, а не обязательно 22.
6. Атомарно установить candidate-конфиг, проверить `sshd -t` и эффективную конфигурацию, затем поддерживаемый reload/restart.
7. С Windows-клиента открыть новый SSH-сеанс на новый порт с закреплённым host key и выбранным ключом, проверить identity и нужные полномочия.
8. Применить окончательную политику; старый доступ убрать только если выбрана эта опция. Проверить effective config и ещё одно свежее ключевое соединение после финальных изменений.
9. Под серверной блокировкой атомарно записать committed и только после этого отключить механизм отката. Commit и rollback взаимоисключающие; при истечении срока commit запрещён.

Отмена до commit запускает компенсацию; при потере сети приложение показывает, что откат ожидается, а не что он доказан. Завершение со статусом rolled back допустимо только после проверки серверного результата. После падения приложения восстановить состояние по transaction ID.

Откат восстанавливает собственные конфиги/ключи/sudoers/port mappings и правила, сохраняя сторонние изменения либо обнаруживая конфликт. Не выполнять общий flush ruleset или restore поверх чужой конфигурации. Не удалять данные появившегося пользователя. Установка пакетов — отдельная подготовительная операция, не обещать универсальный downgrade/uninstall.

Ручной откат после commit — отдельная явно подтверждаемая операция с проверкой нового доступа, поскольку может отключить текущий путь управления.

## 8. SSH-политика и файрвол

PasswordAuthentication no и KbdInteractiveAuthentication no включаются после доказанного ключевого входа; поддержка старого имени ChallengeResponseAuthentication определяется возможностями. PermitEmptyPasswords no, PubkeyAuthentication yes. MFA нельзя совместить с безусловным запретом keyboard-interactive: отдельный согласованный профиль AuthenticationMethods.

PermitRootLogin по умолчанию prohibit-password, no после проверки альтернативного администратора. Если автоматическое применение требует привилегированного контроля, нельзя считать достаточным нового пользователя без sudo.

MaxAuthTries, LoginGraceTime, MaxSessions/MaxStartups и keepalive изменять с объяснением последствий. Forwarding, X11, crypto allowlists, banners и host-key rotation не включать незаметно. Смена порта снижает шум, но не заменяет обновления и ключи. Не добавлять устаревший Protocol 2 в конфигурацию без проверки поддержки.

UFW/firewalld использовать через их API/CLI; у firewalld учитывать runtime/permanent и конкретные zones. Не смешивать управляемые правила с raw nft/iptables. Несколько менеджеров, Docker/Kubernetes/VPN и нераспознанная фильтрация требуют отказа от автоматического изменения.

Не включать deny incoming и не менять глобальную политику на основании `ss`. Внешний firewall провайдера приложение без отдельной интеграции не меняет; новый порт проверяется фактическим внешним SSH-сеансом.

## 9. Fail2ban

Использовать пакетную версию и подходящие backend/banaction. При отсутствии поддерживаемой версии предложить подготовительную установку; не подменять fail2ban самодельным ipset-скриптом.

maxretry 3 и findtime 10m — настраиваемые значения, обозначающие события фильтра, не TCP-подключения. Безопасное начальное bantime — ограниченное время. Бессрочный -1 требует отдельного подтверждения, проверенной БД и теста восстановления после service restart и reboot.

Whitelist включает loopback и подтверждённый адрес, видимый серверу через SSH_CONNECTION. За NAT/VPN/bastion он может отличаться от публичного адреса Windows. Дополнительные IPv4/IPv6/CIDR валидировать, показывать последствия широкого whitelist.

Проверять `fail2ban-client -t`, статус jail, источник логов и совместимость фильтра с OpenSSH. Не нарушать существующие jail. Вкладка банов: список, снятие бана, явное добавление whitelist, CSV без spreadsheet injection.

## 10. Секреты и журнал

Не передавать пароли и passphrase в аргументах процессов, скриптах предпросмотра или переменных окружения сервера; использовать защищённый канал stdin без эха и не смешивать поток sudo-пароля с произвольным скриптом. Валидировать и корректно quote все shell-аргументы; base64 не является шифрованием.

Логировать операции, коды результата и безопасные диагностические сведения. Сырые stdout/stderr могут содержать секреты; не сохранять их без контроля. Защищать известные секреты в исключениях и отчётах. Обнулять контролируемые byte[]; не обещать полное отсутствие копий .NET strings в памяти или дампах.

Локальные бэкапы серверных конфигов требуют DPAPI/ACL и политики удаления. Полный автоматический бэкап `/etc/ssh` не должен вывозить приватные host keys.

## 11. UI и дополнительные модули

Основной маршрут: подключение → аудит → параметры → предпросмотр → применение/проверка → отчёт. Показать уровень риска, действие отката, крайний срок и transaction ID. Асинхронные операции, отмена, отсутствие блокировки UI. Критические действия подтверждать конкретным перечнем последствий.

Отчёт HTML/Markdown: что проверено/изменено, ограничения, новый порт/логин, host/public-key fingerprints, команды подключения и OpenSSH config. Экранировать HTML и shell, не экспортировать секреты. PDF, массовое применение, 2FA, обновления ОС, уведомления, NTP, restricted sudo/SFTP, агенты, PuTTY export и signed auto-update — отдельные целевые модули; отсутствие реализации явно отражать в статусе.

## 12. Архитектура и приёмка

Отделить Core, Ssh, Profiles, Reports и WPF App. SSH и генерацию плана тестировать без UI; зависимости внедрять через интерфейсы. Каждая серверная мутация имеет предусловия, проверку и компенсацию. Ошибки и неизвестные состояния не подавлять успешным статусом.

Обязательные тесты:

- Unit: валидация wire-format/аргументов, shell injection, unsupported profile, отсутствие секретов в плане, порядок pipeline, host-key pinning, отмена, ошибки до/после arming, взаимное исключение commit/rollback.
- SSH integration в контейнерах: реальная аутентификация, отказ trust callback, выполнение команды, sudo, Unicode/крупный вывод, таймаут и отмена. Docker не доказывает firewall/systemd/SELinux/reboot.
- VM acceptance на каждом заявленном сочетании: два порта, ключ+sudo, финальная парольная блокировка, reboot до commit, обрыв сети, закрытый внешний порт, заполненный диск, read-only FS, конфликт конфигов, таймер и восстановление банов.
- Повторное применение без дублей; сохранность чужих firewall rules и пользователей; отсутствие секретов в настройках/отчётах/логах.
- Windows publish/installer smoke на чистой машине; RU/EN, DPI, закрытие окна во время операции и restart recovery.

Критерий выпуска: опубликована матрица с датой, версиями и фактическими результатами, тесты CI проходят, критические fault-injection/VM сценарии подтверждены, подписанные артефакты проверены. До этого версия — предварительная, а не production-ready.
