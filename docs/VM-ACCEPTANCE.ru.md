# Приёмка на виртуальных машинах

Это план проверки, **не журнал пройденных испытаний**. Результаты сохраняйте отдельно с датой, commit SHA, образом/версией ОС, OpenSSH, init, firewall, fail2ban и SELinux. Docker-проверки SSH и скриптов не доказывают поведение реальных systemd timers, firewall, SELinux и reboot.

Используйте одноразовые VM со snapshot и консолью гипервизора. Для положительных сценариев нужны sudo/visudo, runuser и при SELinux — semanage/restorecon. Не изменяйте рабочие серверы ради тестирования.

## Матрица

| ОС | Проверяемая комбинация |
| --- | --- |
| Debian 12, 13 | systemd, ssh.service, нет firewall / активный UFW; IPv4 и IPv6. |
| Ubuntu 22.04, 24.04 | systemd, service-based ssh, UFW; socket activation отдельно как ожидаемый отказ без мутации. |
| Rocky / AlmaLinux 9 | systemd, sshd.service, firewalld runtime/permanent, SELinux enforcing. |
| Alpine/OpenRC, CentOS 7, raw nft/iptables | Аудит и ожидаемый отказ automatic apply; отсутствие частичных изменений. |

## Основные сценарии

1. Сверить host fingerprint; заменить ключ сервера и убедиться в отказе до аутентификации. Проверить, что смена SSH-порта сохраняет pin.
2. Выполнить аудит и план. Изменить входные параметры: прежний план должен аннулироваться. Чужие/невалидные Match, ListenAddress, нестандартный Include и SSH command-line override должны приводить к контролируемому отказу. Собственные Match допускаются только с проверенным root-owned proof; политики других аккаунтов сохраняются.
3. Применить новый порт и новый RSA/Ed25519-ключ. На dual-фазе исходный вход ещё работает. Для Legacy подтвердить два свежих key/sudo сеанса; для advanced — target role/MFA и отдельный управляющий вход согласно разделу ниже. После final парольный вход запрещён, а старый порт закрыт только при выбранной опции.
4. Включить active firewall; сохранить посторонние правила. Проверить добавление только собственных правил, runtime/permanent у firewalld и обе IP-семьи. Откат должен сохранять чужие allow/deny и сервисы.
5. Повторить настройку в режиме существующего пользователя: ключи/правила не дублируются, чужие ключи и данные сохраняются. Создание пользователя с уже занятым именем отклоняется.

## Сбои и восстановление

- Оборвать сеть/закрыть приложение после arming, provision, dual и final. Проверить возврат исходного доступа по таймеру и точный статус rolled-back.
- Перезагрузить VM до commit. Проверить boot recovery до запуска SSH и доступ с исходными параметрами; после commit reboot не должен отменять операцию.
- Заблокировать новый порт во внешнем firewall. Новая проверка должна провалиться, commit отсутствовать, старый доступ восстановиться.
- Имитировать заполнение диска, read-only FS, неверный candidate и отказ reload; проверить, что ошибка не выдаётся за успех. При невозможности компенсации статус recovery-failed и инструкция консоли доступны.
- Изменить main/Include-конфиг параллельно, запустить вторую транзакцию и столкнуть commit с таймером. Конфликт не должен приводить к двойной фиксации/удалению чужих данных.
- Проверить ручной rollback последнего commit с консоли; более старый commit и конфликты конфигов должны отклоняться. Учесть отзыв sudo у текущей учётной записи.
- Перезапустить Windows-приложение после завершённой и прерванной операции. История должна загрузиться без сети и секретов; исходное/новое подключение подставляется только выбранной кнопкой. После ввода секретов проверить состояние на том же host key. Старый локальный статус, несовпадение сервера, ошибка чтения и выбор другой операции не должны разрешать ручной откат. Перед откатом повторно проверить серверное состояние и запрет более старого commit.

## Новые роли, MFA, SFTP и массовый Apply — ещё не приняты на VM

Положительные сценарии выполнять с заранее установленным Python 3, независимо сохранённым original-admin ключом и консолью. Для автоматической установки отсутствующего Google PAM на Debian/Ubuntu выбрать recovery deadline не менее 10 минут; на RPM модуль подготовить заранее. Повторить с чужими sudo/PAM/Match/proof, симлинками и изменениями между фазами: отказ не должен перезаписывать чужие файлы.

- Для Password/Passwordless/None/Restricted подтвердить фактические sudo-права после свежего входа. Existing Password hash не меняется; новый пароль при rollback блокируется только при совпадении собственного hash. Чужие полные/частичные grants в ограничиваемых/парольных режимах должны блокировать preflight. Для Restricted проверить точные разрешённые команды, запрет shell/wildcard/pager, writable unit/exec отказ и доверие к конфигурации разрешённой службы.
- Для None/Restricted/SFTP-only target должен отличаться от управляющего администратора. Password-only control, отсутствующий ключ, неверный pin и запрещённый итоговый root login должны отказать до опасных изменений. После final нужен **реальный fresh source-admin key login на новый порт + root0**, затем commit. Потеря этого доступа должна исключить commit и запустить проверяемое recovery.
- Для нового SFTP-only подтвердить chroot, `/uploads`, RW либо `-R`, отсутствие shell/TTY/forwarding/tunnel/X11 и ключ вне chroot. Проверить настоящий production SFTP client и браузер, запрет symlink/overwrite без согласия, `.partial` cleanup и отмену. Повторный Apply к уже управляемому SFTP пока является ожидаемым отказом до arming, а не пройденным reapply-сценарием.
- Для нового MFA подтвердить ручной enrollment, восемь сохранённых recovery codes, key+OTP и два final входа с разными time steps; неверный/пропущенный/reused code должен отказать. Подтвердить single-use recovery, RATE_LIMIT, дрейф часов и сохранность доступа других аккаунтов. Проверить root-only secret/proof и штатный переход mode 0600→0400. При EnableTotp=false прежняя MFA сохраняется и требует настоящий код; повторный enrollment managed MFA пока должен отклоняться до arming. Для новой службы/другого пользователя прежние owned blocks нельзя удалять на dual-фазе.
- Прервать production apt-установку PAM при занятой package lock/обрыве/отмене; stdin пакетов не должен содержать credentials. Проверить recovery-deferred, retry, root-only logs, сохранение установленных пакетов и возврат исходного доступа. Повторить fault/reboot до и после PAM/secret/sudoers/Match mutation, включая конфликт конфигов и употреблённые recovery codes.
- На двух и более disposable VM пройти bulk preview→Apply с concurrency 1 и 4, индивидуальными pins/историей, уникальным MFA enrollment, отказом одного хоста, stop-on-first-failure и отменой. Сверить Committed/RolledBack/Unconfirmed/Skipped отдельно; общего атомарного rollback не ожидать. Не выполнять этот тест на рабочих серверах.

Сканировать profiles/history/CSV/reports/logs на синтетические маркеры password/seed/recovery codes. Проверить RU/EN, DPI, диалоги enrollment/OTP/credentials и закрытие во время transfer/Apply; локальную отмену не считать доказательством уничтожения всех remote descendants. Новые fixture-результаты из VALIDATION не заменяют ни один из этих full Apply/PID1/VM сценариев.

## Fail2ban и клиент Windows

С отдельного НЕ-whitelisted тестового адреса отправить подходящие фильтру неудачные события. Проверить бан, whitelist IPv4/IPv6, unban и повторное чтение логов. Для bantime=-1 отдельно подтвердить восстановление ban после service restart и reboot; не считать число TCP-соединений равным maxretry.

На чистой Windows-машине проверить portable и per-user installer, RU/EN, масштабирование DPI, светлую/тёмную тему, отмену, закрытие во время операции и восстановление после запуска. Просмотреть настройки, логи и отчёты на тестовые маркеры секретов; HTML/Markdown не должны выполнять серверный текст. Проверить подпись реально подписанного выпуска отдельно от unsigned CI artifact.

Критерий принятия комбинации: все применимые сценарии имеют фактические результаты и воспроизводимые доказательства; неизвестные результаты не считаются PASS.
