# Проверка предварительной версии 0.1

Дата: 6 ноября 2026 года. Автор приложения: @victoryur.

## Выполнено локально

- Release-сборка на Windows x64 с .NET SDK 10.
- 190 автоматических тестов: проверка входных данных и ключей, шифрованный RSA PKCS#8/PPK v3 round-trip, сохранение исходника и отпечатка при экспорте, отказ при неверной фразе или подмене MAC/шифротекста/комментария, защита от перезаписи файлов и приватные ACL, host-key store, исключение секретов из отчётов, политика алгоритмов, подтверждение root/sudo, последовательность двух новых подключений, потеря commit acknowledgement, отмена и подтверждение отката, восстановление при исключении наблюдателя прогресса, ожидание открытия/закрытия SSH-портов после reload, параметры Fail2ban, порядок установки после arming и 13 проверок строгого распознавания собственных правил firewall.
- POSIX shell parser проверил все сгенерированные скрипты, включая вложенные heredoc для отката и операций пользователя. Скрипты при этой проверке не выполнялись.
- WPF self-test создал настоящие элементы интерфейса и проверил 48 сочетаний: 6 вкладок × RU/EN × светлая/тёмная тема × 1180×820/920×640. Изображения просмотрены; дополнительно в настоящем окне проверены нижняя часть настроек, прокрутка и открытые списки в обеих темах. Подключения к серверу при визуальных проверках не выполнялись.
- Отдельный WPF regression harness воспроизвёл ошибку согласованности ItemsControl со старой синхронной автопрокруткой. Исправление прошло проверку реального окна: поток progress, ограничение журнала в 1000 записей, переключение вкладок, очистка, автопрокрутка и закрытие с отложенным обновлением. Сбой UI немедленно отменяет активную операцию, ждёт независимое восстановление и запрещает новые операции. Проверка выполняется без сети и пользовательских секретов, включена в CI.
- Self-contained single-file EXE и установщик Inno Setup собраны локально. Проверочные сборки не имеют подписи автора.

## Реальная SSH-интеграция

В Docker внутри существующей Ubuntu WSL подняты изолированные Debian 12, Ubuntu 24.04 и Rocky Linux 9. На всех трёх успешно проверены:

- вход по паролю и зашифрованному приватному ключу;
- NOPASSWD sudo и sudo с паролем через stdin;
- передача скрипта через stdin, stderr и ненулевого exit code;
- отказ при неподтверждённой идентичности, в том числе для уже известного endpoint;
- аудит ОС, полномочий и адреса администратора при sudo;
- запрет автоматического применения без systemd;
- выполнение настоящего скрипта создания пользователя, установки ключа, прав доступа и sudoers;
- новый вход созданным ключом и получение root через sudo;
- автоматическое выполнение тела восстановления и ручной откат подготовленного committed-состояния, включая отзыв собственного sudo и ключа; учётная запись и её файлы сохраняются.

В сценариях provisioning/recovery проверка systemd заменена тестовой командой внутри контейнера. SSH, PAM, sudoers, useradd, runuser, файловые разрешения и удаление доступа выполняются реально. Полная транзакция ApplyAsync на systemd-хосте этим не подтверждается.

Отдельный одноразовый Debian-контейнер воспроизвёл задержку обработки SIGHUP настоящим sshd через SIGSTOP/SIGCONT. Мгновенная проверка нового порта не прошла; производственная функция ожидания успешно проверила dual, закрытие старого порта в final и возврат исходного порта при recovery. Использовались настоящие sshd/ss, без публикации портов на хосте; systemctl is-active был заменён проверкой процесса. Это проверка гонки listener, а не полной systemd-транзакции.

## Проверка Fail2ban

На отдельном Debian 12 проверена настоящая установка отсутствующих Fail2ban, journal backend и средств packet filter. Три неверных пароля и три неверных ключа давали бан, первые две ошибки — нет; бан блокировал успешную аутентификацию, снятие бана возвращало вход. Собственные правила принимались read-only probe, чужое правило INPUT и чужая nft table отклонялись. Занятая package lock переводила production rollback в recovery-deferred с сохранением масок/конфигурации и запросом повтора; после освобождения блокировки откат возвращал состояние службы, удалял только собственные файлы и сохранял чужой конфиг и установленные пакеты. См. [воспроизводимый сценарий](../tests/SSHHardener.IntegrationTests/Fail2BanScenario.README.md). Использовались настоящие apt, sshd, journald, Fail2ban и netfilter в отдельном container namespace; управление службами заменено fixture shim, реальный boot этим не подтверждается.

## Результат VM

На Debian 12/systemd выполнен полный Apply из Windows-приложения с отключённым модулем Fail2ban: preflight, arming, provision, dual-port, два независимых ключевых входа с sudo, final и подтверждённый committed.

6 ноября 2026 года, около 13:06 МСК, подтверждён повторный полный Apply с **включённым новым модулем Fail2ban**. Предварительный аудит показывал, что Fail2ban не установлен. После arming этап установки и настройки успешно завершился, затем прошли provision, dual-port, первый новый ключевой вход с sudo, final, второй новый ключевой вход с sudo и commit. Итог: committed=true, rolledBack=false.

Успешный этап настройки включает проверку фактических параметров управляемого jail через `fail2ban-client get`: maxretry=3, findtime=600 секунд, bantime=3600 секунд. На этапе final также проверены эффективные MaxAuthTries=3 и LogLevel=VERBOSE для SSH. Реальная установка отсутствовавшего Fail2ban и проверка этих параметров в составе полного Apply подтверждены кодом обязательных проверок, отчётом пользователя и локальным журналом успешно завершённых этапов приложения. Это не отдельный post-change аудит.

Блок Audit в HTML-отчёте — **снимок до изменений**. Поэтому запись об отсутствии Fail2ban относится к исходному состоянию и не описывает состояние после успешной установки. Этот снимок нельзя считать повторным аудитом после commit; экспорт явно помечает его происхождение.

В тот же день пользователь выполнил со второго ноутбука пять попыток SSH-входа с одноразовым неверным Ed25519-ключом; все пять завершились отказом publickey. После них статус управляемого jail показал: Currently failed=1, Total failed=5, Currently banned=1, Total banned=1. В списке блокировок находился отдельный адрес второго ноутбука. Дополнительная попытка с этого адреса после проверки статуса завершилась тайм-аутом соединения. Таким образом, на VM подтверждены учёт отказов, зарегистрированный бан и последующая недоступность SSH с заблокированного источника.

Момент срабатывания бана между попытками не фиксировался: этот VM-сценарий не доказывает блокировку ровно после третьей попытки. Порог maxretry=3 ранее проверен в runtime, а последовательность «после первых двух ошибок бана нет, после третьей есть» подтверждена отдельным контейнерным тестом выше.

## Повторное применение и ручной откат

6 ноября около 15:44 МСК пользователь повторно выполнил полный Apply на существующей учётной записи с переходом порта 22022 → 22033. Локальный журнал подтверждает два новых key/sudo сеанса, final и committed=true. После повторного подключения и проверки состояния пользователь выполнил ручной откат из приложения: операция завершилась успешно, экспортированный результат содержит committed=false, rolledBack=true и сообщение о серверном подтверждении отката. Это подтверждает реальный ручной откат на Debian 12; отдельное новое подключение с исходными параметрами после него пока не подтверждено. В этом прогоне приложение между Apply и rollback не перезапускалось, поэтому приёмка восстановления после перезапуска остаётся отдельным шагом.

После запуска обновлённой сборки локальная история сохранилась: в интерфейсе наблюдалась выбранная операция с последним подтверждением «Откат выполнен» в 15:44. Кнопки проверки сервера и отката до подключения оставались выключенными. Это подтверждает загрузку пользовательской записи после перезапуска; свежий запрос серверного состояния после этого запуска ещё не выполнялся.

Экспорт после rollback исправлен: команда подключения и параметры клиента показывают исходный порт, пользователя и способ аутентификации, а не отменённый целевой endpoint. Предварительный аудит остаётся явно обозначенным снимком до изменений. Добавлен 21 regression-сценарий для MD/HTML/JSON: rollback, commit, неизвестный результат, сохранность секретов и отказ объединять разные transaction ID; общий прогон 190 тестов и WPF regression завершились успешно.

## Совместимость ключей

PuTTYgen 0.78 в отдельном контейнере независимо расшифровал и проверил MAC созданного приложением encrypted PPK v3, переэкспортировал приватную часть в зашифрованный OpenSSH, подтвердил тот же публичный ключ и отклонил неверную парольную фразу. Два зашифрованных представления одного RSA-ключа — исходный PKCS#8 и экспортированный PPK v3 — успешно аутентифицировались через SSH.NET на одном loopback SSH fixture без изменения authorized_keys. Секреты передавались независимому инструменту через stdin; аргументы процессов и временные файлы не содержали пароль или расшифрованный приватный ключ. См. [повторяемую проверку](../tests/SSHHardener.IntegrationTests/PuttyInterop.README.md).

Пользовательская ошибка `Unsupported pkcs8 encryption (pkcs8 v2.0)` зафиксирована в RDM 2026.2.14.0. После экспорта ключа в PPK пользователь подтвердил успешное SSH-подключение из RDM сообщением и скриншотом; на скриншоте также виден переход к root через su. Это подтверждение конкретного пользовательского сценария, а не полной матрицы версий и SSH-движков RDM. Пользовательский приватный ключ при этой проверке агентом не читался; парольную фразу для экспорта пользователь вводил сам в приложении.

## История операций и повторный запуск

Добавлена история операций с минимальным DTO без паролей, парольных фраз, приватных ключей, аудита и скриптов плана. Файл защищён DPAPI CurrentUser и ACL текущего пользователя; запись атомарно заменяется после flush, конкурентные процессы используют файловую блокировку. Незавершённые записи не вытесняются, при заполнении истории подтверждённые NotFound могут освобождать место. Ошибка сохранения до Apply не позволяет запустить engine.

Новые автоматические проверки покрывают сериализацию без секретов, шифрование и ACL, повреждение и подмену файла, отмену и конкуренцию, неизменяемую привязку операции, ограничения размера и retention. Чтение серверного статуса проверяет endpoint и host key до запроса, строго разбирает ответ и не выдаёт неизвестное состояние за успех.

Настоящий WPF regression harness проверил загрузку истории в новом экземпляре ViewModel без сети, подстановку двух подключений с очисткой секретов, запрет отката по cached committed, проверку host pin, сброс разрешения после ошибки/смены выбора, повторное чтение latest commit перед ручным откатом и отсутствие Apply при повреждённом history. Проверен порядок: сохранённая запись существует до первого вызова engine. Снимки заполненной истории RU/light и EN/dark при 920×640 просмотрены. Это fixture-проверки без подключения к пользовательской VM.

Точный production shell probe прошёл 24 проверки в одноразовом Debian Docker без сети и дополнительных capabilities: все состояния, latest commit, безопасное отсутствие, неверные права/владелец, симлинки, повреждённое состояние и настоящая блокировка flock. Конфликт блокировки проверяется до сообщения NotFound. См. [воспроизводимый сценарий](../tests/SSHHardener.IntegrationTests/TransactionStatusScenario.README.md). Исполнение серверного rollback или boot этим сценарием не подтверждается.

Release build завершился без предупреждений и ошибок, locked restore и self-contained win-x64 publish прошли. Опубликованный EXE прошёл восемь startup/layout проверок вкладки истории: RU/EN, светлая/тёмная тема и ширина 1180/920.

## Оставшаяся VM-приёмка

На этой VM ещё не проверены разбан и возврат доступа после него, а также точный момент срабатывания порога по каждой попытке. Подтверждение бана и тайм-аута после него описано выше; успешный полный цикл «три ошибки → бан → разбан → восстановленный вход» пока проверен только в отдельном контейнерном сценарии.

Не проверены восстановление новой истории с повторным подключением на пользовательской VM, новое подключение с исходными параметрами после ручного отката, реальное срабатывание timer/boot recovery при потере клиента, потере питания/перезагрузке, SELinux enforcing, UFW/firewalld и восстановление бессрочных fail2ban-банов. Не проверены внешние security groups, NAT и поведение провайдеров. Поэтому версия остаётся предварительной; заявлять production-ready или полную матрицу дистрибутивов нельзя.

Целевое ТЗ содержит дополнительные модули, которые отсутствуют в этой версии: socket activation, OpenRC, произвольные nft/iptables-конфигурации, установка RPM-зависимостей, Ed25519-генерация, restricted sudo, chroot/SFTP, 2FA, массовые задания и обновление приложения. Приложение блокирует неподдерживаемые опасные сценарии.
