# Восстановление доступа

До применения сохраните transaction ID и обеспечьте доступ через консоль провайдера или гипервизора. Изменения внешних security groups, отказ диска и отсутствие питания серверный таймер исправить не может.

## Восстановление в приложении после перезапуска

1. Откройте вкладку «Применение» и выберите запись в «Истории операций». История создаётся до начала применения и не содержит паролей, парольных фраз, приватных ключей или исполняемого плана.
2. Нажмите «Исходное подключение» или «Новое подключение». Программа подставит адрес, порт, имя пользователя и путь ключа, очистит поля секретов и откроет вкладку подключения. Введите секреты заново.
3. Подключитесь. Программа проверит публичный ключ сервера по выбранной операции до аутентификации, выполнит аудит полномочий и запросит состояние операции. Для повторного запроса доступна кнопка «Проверить состояние».
4. При недоступности сервера состояние не считается подтверждённым. Запись «последнее подтверждение» относится к прошлой проверке и сама по себе не разрешает откат.
5. Для доступного отката нажмите «Откатить последнюю транзакцию…». Перед выполнением программа ещё раз прочитает состояние, покажет номер операции и последствия. Сервер дополнительно проверяет блокировку, допустимость отката и конфликты; более старый commit откатывать нельзя.

Запуск программы только загружает локальную историю: он не подключается, не повторяет план и не запускает откат. Если выбранная операция относится к другому серверу или его публичный ключ изменился, восстановление через эту запись запрещается. Во время уже выполняющегося отката повторный ручной запрос недоступен.

История защищена DPAPI CurrentUser и ACL текущего пользователя Windows. Повреждение файла не считается пустой историей, а невозможность сохранить запись о новой операции останавливает её до изменений на сервере. Обновление локального статуса после завершения не меняет уже подтверждённый результат на сервере. Перенос зашифрованного файла в другую учётную запись Windows не обеспечивает его чтение.

Операции более ранних версий без локальной записи автоматически не импортируются. Для них используйте сохранённый transaction ID и консольные шаги ниже.

## Если операция прервалась

Не запускайте новую транзакцию поверх незавершённой. Попробуйте исходный порт и исходную учётную запись, затем новый порт с выбранным ключом. Не принимайте изменившийся host key без независимой проверки. Сообщение «recovery is not confirmed» не означает успешный откат: приложение не смогло доказать результат.

На консоли сервера от root проверьте состояние. В примерах замените `20261106120000-abcdef123456` идентификатором своей операции:

```sh
txid=20261106120000-abcdef123456
cat /var/lib/ssh-hardener/transactions/$txid/state
systemctl status ssh-hardener-$txid.timer ssh-hardener-$txid.service
journalctl -u ssh-hardener-$txid.service -u ssh-hardener-$txid-boot.service
```

`pending` — операция ожидает завершения; `rolling-back` — выполняется компенсация; `rolled-back` — скрипт подтвердил завершение; `recovery-failed` — часть действий не удалась. `committed` означает зафиксированную операцию, которую автоматический таймер больше не отменяет.

`recovery-deferred` означает, что пакетный процесс ещё удерживает свою блокировку. Скрипт сохраняет временные маски и защищённую конфигурацию, запрашивает повтор восстановления через 20 секунд и оставляет boot recovery. Это не успешный откат. Не удаляйте блокировки и маски вручную; проверьте процесс и root-only файл `fail2ban.packages.log` в каталоге транзакции. После прерванного dpkg может потребоваться восстановление пакетного менеджера. При успешном откате новые пакеты остаются установленными, а собственные настройки и состояние служб возвращаются к исходным.

## Повторить незавершённый откат

Сначала убедитесь, что это нужный сервер и нет другого администратора, меняющего настройки. Для незавершённой операции:

```sh
/bin/sh /var/lib/ssh-hardener/transactions/$txid/rollback.sh auto
cat /var/lib/ssh-hardener/transactions/$txid/state
/usr/sbin/sshd -t
ss -ltnp
```

Скрипт берёт серверную блокировку и не отменяет уже committed-транзакцию в режиме auto. Не удаляйте `/var/lib/ssh-hardener/active` и файлы состояния вручную для обхода проверки: это может нарушить восстановление.

После восстановления выполните новое SSH-подключение извне. Проверьте firewall провайдера, runtime/permanent правила firewalld или правила UFW, а также SELinux. Не выполняйте общий flush файрвола: это может повредить доступ других сервисов.

## Ручной откат после commit

Кнопка ручного отката и режим `manual` могут отключить текущий ключ и отозвать выданный sudo. Используйте их с консолью провайдера и проверенными исходными данными доступа. В этой версии разрешён только последний commit при неизменившихся SSH-файлах; конфликт требует ручного разбора через консоль.

```sh
/bin/sh /var/lib/ssh-hardener/transactions/$txid/rollback.sh manual
```

Новая учётная запись и её данные сохраняются; приложение убирает собственный ключ и выданные разрешения. Серверный бэкап содержит исходный `sshd_config`; приватные host keys на Windows не вывозятся. При `recovery-failed` изучите журнал, права и свободное место, исправьте причину и повторите восстановление с консоли. Успех команды не заменяет новое внешнее подключение.
